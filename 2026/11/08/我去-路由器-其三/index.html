我去！路由器！其三

当你看到这篇文章时，我就假装你已经有了一个提取好的固件。

在路由器的固件的分析过程中你可能会遇到两种不同系统所产生的固件，一种是基于 Linux 的带文件系统的组合压缩包，这种相对好分析一点，另外一种是基于 VxWorks 的一体化可执行文件系统压缩包，这种常见与另类的老版路由器，不是特别好分析，本文章先从简单入手。

裸扫只吐了一个 uImage

有意思的在这儿。

先不递归，只做一遍纯扫描：

输出短得可疑：

就一条，还是 uImage 的头部信息。

说好的内核呢？说好的文件系统呢？一个 SquashFS、一个 CramFS 都没有。

原因写在那行 description 里了：compression: lzma。

这固件后面那一大坨数据是整块被 LZMA 压过的，压完就是一段熵接近满值的高熵数据。

而 binwalk 干的是特征码扫描——它在文件里找 magic bytes。压缩之后，原来 hsqs（squashfs）或者 cpio 的 070701 全成了乱码，一个都认不出来。

也就是说 binwalk 没瞎，是它根本看不见里面。

再加上 binwalk3 默认只汇报最外层：扫到什么报什么，扫完这一层就结束，不会主动把压缩数据解开再扫一遍。

所以裸 binwalk 能看到的，永远只有没被压的那层壳。

想让它钻进去，只能靠 -M。

同理，要是换成一块加密过的固件，-Me 也白搭——熵图拉出来是一条平直的高线，binwalk 一个特征都吐不出来。

那种情况就别指望工具了，老老实实去找串口、找启动日志、找加密逻辑，或者干脆上夹子读 Flash。

找服务启动链

固件抠出来了，然后呢？

一个根文件系统里几百上千个文件，光扫一眼是看不出东西的。

分析文件系统的第一个目的，永远是找服务启动链——顺着它走一遍，你就知道这台设备开机之后到底跑了些什么，哪些端口在听，哪个进程在处理你的 HTTP 请求。

这条链通常就三个东西：init → 启动脚本/二进制 → 各个服务。

从 init 开始

一般 Linux 都从 init 开始启动，init 再一层层配置环境、拉起服务。

先看它是什么玩意儿：

init 是个软链接，它一般是软链接，这一点很关键。

指向的东西有两种常见情况：

  1. 指向一个 shell 脚本 —— 那就是传统的 rcS 那一套，直接 cat 就能读完，最省事。
  2. 指向一个二进制 —— 那就得拖进 IDA 里啃了。

只要有人在串口上敲个回车，就掉一个 /bin/login 或者 /bin/sh 下来。

这在物理接触的场景里是常规操作，但意义在于：它不需要密码就能先拿到 shell 的入口——login 起来了才输密码，而如果 login 本身有问题，就直接进 sh 了。

execve 第二个参数用的 off_45E190、off_45E19C 这些，是 argv 数组，也就是各种登录名。

本地取 shell 的门槛，就是”物理接触 + 串口 + 敲个回车”。

逻辑很干净：

  1. 用 kill(pid, 0) 探活，信号 0 不改进程状态，只检查存在性。
  2. 进程死了就 pidof 找一遍，可能是 fork 之后 PID 变了。
  3. 还找不到就调 start_xxx() 重新拉。

kill(pid, 0) 这个技巧比 ps | grep 可靠得多，也不会被同名进程骗到。嵌入式里到处都在用。

注意 jhttpd_stop 那个分支：只要 nvram 里 jhttpd_stop 被设成真，Web 服务就不会被拉起，也不会被看门狗救回来。

init_main 开头自己也把它清过一遍（nvram_set("jhttpd_stop", "0")），开机先确保 Web 是要起来的。
